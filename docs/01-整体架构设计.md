# vocara 呼叫中心系统 — 整体架构设计

## 1.1 架构总览

Vocara 是基于 Go + FreeSWITCH 的呼叫中心系统，采用微服务架构：五个业务服务、
一个公共库、一个跨边界契约模块，通过 go.work 工作区统一管理。

- **业务服务**：admin、agentcenter、acd、callctrl、push，各自独立部署、独立持有数据。
- **公共库 `vocara/pkg`**：config、database、errors、eventbus、logger、middleware、
  redis、response、utils、version 等基础能力。
- **契约模块 `vocara/contracts`**：跨边界事件 DTO 与 HTTP DTO，零业务依赖。
- **核心区**：自研 ESL 客户端 `vocara/core/esl` 与呼叫控制 `vocara/core/callctrl`
  位于独立私有仓库 `core`，以预编译二进制 `vocara-callctrl` 交付到本仓库，业务侧
  编译不接触核心源码。

服务分层遵循 handler → service → repository → model；跨服务调用走 HTTP 或事件，
不直接访问对方存储。

## 1.3 服务职责

| 服务 | 模块名 | 端口 | 职责 |
|---|---|---|---|
| vocara-admin | vocara/admin | 8080 | 管理后台 API：座席、分机、技能组、队列、线路、呼入路由、租户、参数、话单、统计、License、表单 |
| vocara-agentcenter | vocara/services/agentcenter | 8081 | 座席状态机、技能组、分机、座席 Redis 会话 |
| vocara-acd | vocara/services/acd | 8082 | ACD 智能排队：active/paused 双 ZSET + Lua 原子脚本 |
| vocara-callctrl | vocara/core/callctrl | 8083 | 呼叫控制：ESL 事件、呼入呼出、录音、监听/耳语、CDR |
| vocara-push | vocara/services/push | 8084 | WebSocket 实时推送：NATS + Redis 双消费者 |

## 1.4 媒体节点与呼叫编排

FreeSWITCH 采用双节点：FS-SBC 承担接入侧（外部线路接入、客户侧媒体、向 FS-Agent
转发呼入与外呼出局），FS-Agent 承担座席侧（座席分机注册、座席侧媒体、浏览器
WebRTC、呼入 park 与桥接）。callctrl 持有一个 ESL Inbound 客户端，只连接
FS-Agent 统一编排。两个媒体节点的拨号方案均由 admin 经 mod_xml_curl 按节点与
context 实时下发，不落节点磁盘；FS-SBC 的接入转发不经过 callctrl 的 ESL 编排。
FreeSWITCH 只负责媒体与协议处理。

呼入处理链路：

1. 客户呼入 FS-SBC，按 admin 实时下发的 public 拨号规则 bridge 到 FS-Agent，
   通道应答后 park，通道变量 `vocara_did` 记录接入号；
2. callctrl 在 FS-Agent 以呼入路由缓存（admin 动态下发为主、静态路由为回落）
   匹配队列或技能组，进入 ACD 排队；
3. ACD 分配座席（`queue.dequeue`）后，callctrl 将客户腿 `uuid_transfer` 到拨号
   方案扩展 `vocara_agent_<分机>`；
4. 拨号方案以 bridge 应用原生创建座席腿 `user/<分机>`，座席接听即在桥中；
5. 监听 `CHANNEL_HANGUP_COMPLETE` 统一处理挂机与 CDR 生成。

详见 `docs/05-FreeSWITCH_ESL交互层.md`。

## 1.5 服务间通信

| 场景 | 方式 | 说明 |
|---|---|---|
| 同步调用 | HTTP | 内部接口经 InternalAuth 鉴权，携带 X-Internal-Token |
| 状态与话务事件 | eventbus | NATS 优先、Redis 降级（Dual 模式） |
| 对浏览器推送 | WebSocket | 业务服务只发布事件，由 push 消费后路由到连接 |
| 数据访问 | 各自存储 | 不跨服务访问对方数据库 |

## 1.6 事件总线

事件信封字段：`event_id`、`event_type`、`timestamp`、`tenant_id`、`source`、`data`；
主题命名 `vocara.event.{type}`，如 `vocara.event.agent.status_change`、
`vocara.event.cdr.created`。发布者有 NATS、Redis、Dual 三种实现。
业务服务只发布事件，push 的 business_consumer 负责消费并路由到 WebSocket。

## 1.7 话单数据

通话话单落 MySQL：技术明细表 `cdr_calls` 与统一话单表 `tb_call_record`。
`tb_call_record` 使用 MySQL 原生分区。CDR 事件统一为 `cdr.created` 信封，
经 NATS 与 Redis 发布。

## 1.8 多租户

`tenant_id` 贯穿事件信封、话单与各业务数据；座席状态、话务事件按租户隔离，
推送连接建立时自动订阅个人主题、租户主题与全局广播主题。

## 1.9 技术栈

| 类别 | 选型 |
|---|---|
| HTTP 框架 | Hertz |
| ORM / 数据库 | GORM v2 / MySQL 8.0 |
| 缓存 / 客户端 | Redis 7 / go-redis v9 |
| 消息 | NATS JetStream |
| 日志 | zap（zap.Field 风格，结构化 JSON，输出目标随配置在文件与 stdout 间选择） |
| 配置 | viper，snake_case YAML，CONFIG_PATH 可覆盖路径 |
| 鉴权 | JWT |
| ESL | 自研客户端（核心私有仓库 esl：command/event/inbound/outbound/pool/transport） |

请求经过的中间件链顺序为：TraceID → Recovery → CORS → RequestLogger → JWT。
链路追踪由 TraceID 中间件在日志中贯穿；服务存活与就绪状态由 K8s 探针检测。
