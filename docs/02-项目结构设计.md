# vocara 呼叫中心系统 — 项目结构设计

## 2.1 目录结构

系统采用**微服务 + 双仓库**结构：公开仓库 `vocara` 承载业务区 `business/`、契约 `contracts/` 与公共库 `pkg/`；私有仓库 `core` 承载核心区源码，以预编译产物交付到 `vocara`。核心仓库经 go.work 引用 `vocara/contracts` 与 `vocara/pkg`。每个服务内部按「handler → service → repository → model」分层。

```
vocara/
├── go.work                        # 业务工作区（业务服务 + 契约 + 公共库）
├── go.work.sum
├── Makefile                       # 构建与二进制交付流水线
├── run.sh / run.cmd               # 本地开发启动脚本
├── README.md
│
├── contracts/                     # 跨边界契约（module vocara/contracts）
│   ├── event/                     #   事件 DTO：allocated、cdr
│   └── call/v1/                   #   callctrl HTTP DTO：inbound 回调
│
├── pkg/                           # 公共库（module vocara/pkg）
│   ├── config/                    #   配置加载（viper）
│   ├── database/                  #   MySQL 连接（GORM）
│   ├── redis/                     #   Redis 客户端（go-redis）
│   ├── eventbus/                  #   事件总线（NATS / Redis / Dual）
│   ├── logger/                    #   日志（zap）
│   ├── errors/                    #   统一错误码与 BizError
│   ├── response/                  #   统一响应结构
│   ├── middleware/                #   通用中间件（JWT、InternalAuth 等）
│   ├── license/                   #   License 校验运行时
│   ├── version/                   #   构建期注入的版本信息
│   └── utils/                     #   通用工具函数
│
├── business/                      # 业务区（不依赖核心源码）
│   ├── services/
│   │   ├── admin/                 # vocara-admin      :8080 module vocara/admin
│   │   ├── agentcenter/           # vocara-agentcenter:8081 module vocara/services/agentcenter
│   │   ├── acd/                   # vocara-acd        :8082 module vocara/services/acd
│   │   └── push/                  # vocara-push       :8084 module vocara/services/push
│   └── web/
│       ├── admin/                 # 管理后台前端（Vue3 + TS + Vite + Naive UI）
│       │   └── public/            #   混淆电话条 phonebar/ 与动态表单 SDK form/ 产物
│       └── form/                  # 动态表单 SDK（Vite 库模式）
│
├── bin/                           # 核心预编译二进制（vocara-callctrl，linux + windows）
├── configs/                       # 核心运行期配置模板（callctrl.yaml）
│
├── db/migrations/                 # 数据库 DDL 脚本
└── deploy/
    ├── docker/                    # Dockerfile：backend（业务四服务）/ callctrl / web
    └── k8s/                       # Kubernetes 部署清单
```

核心源码位于独立私有仓库 `core`（与 `vocara` 同级）：
```
core/
├── go.work                        # 核心工作区（use ../vocara/pkg ../vocara/contracts + 自身模块）
├── esl/                           # 自研 FreeSWITCH ESL（module vocara/core/esl）
├── callctrl/                      # 呼叫控制（module vocara/core/callctrl）
├── phonebar/                      # 电话条 SDK（混淆构建，通用产物）
├── freeswitch/                    # FreeSWITCH 配置（fs-sbc / fs-agent conf）
└── tools/license-cli/             # License 签发工具（module vocara/license-cli）
```
核心仓库经 `make sync` 把 `bin/vocara-callctrl(.exe)`、混淆电话条与 callctrl 配置模板
发布到 `vocara`。免编译部署 vocara 时无需核心仓库。FreeSWITCH 配置不进入 sync 产物，
由运维从核心仓库 `freeswitch/` 目录直接部署。

单个服务的标准结构（以 admin 为例）：

```
business/services/admin/
├── cmd/main.go                    # 启动入口
├── configs/config.yaml            # snake_case 配置
└── internal/
    ├── handler/                   # HTTP 接口层
    ├── service/                   # 业务逻辑层
    ├── repository/                # 数据访问层
    └── model/                     # 数据模型
```

按职责差异，acd 在 `internal/` 之外另含 `scripts/`（Lua 脚本与 `//go:embed` 嵌入包）；push 的 `internal/` 含 `consumer/`（事件消费）；callctrl 的 `internal/` 含 `eslhandler/`（ESL 事件处理）。

## 2.2 包命名规范

| 类别 | 命名规范 | 示例 |
|------|---------|------|
| 服务内分层目录 | 小写单数名词 | `handler/`、`service/`、`repository/`、`model/` |
| Handler 层 | `handler` | `internal/handler/xxx_handler.go` |
| Service 层 | `service` | `internal/service/xxx_service.go` |
| Repository 层 | `repository` | `internal/repository/xxx_repository.go` |
| Model 层 | `model` | `internal/model/xxx.go` |
| 公共库 | `pkg/<name>` | `pkg/errors/`、`pkg/eventbus/` |
| 契约 | `contracts/<domain>` | `contracts/event/`、`contracts/call/v1/` |

**Go 包命名原则：**

1. 全小写，不加下划线。
2. 见名知意，不使用缩写（除公认的 `cfg`、`ctx`）。
3. 避免与标准库重名（不使用 `log`、`http`、`json` 等）。

## 2.3 代码分层职责

### 2.3.1 Handler 层（接口适配层）

**职责：**

- 接收 HTTP / WebSocket 请求，完成参数绑定与校验
- 调用 Service 层
- 通过 `pkg/response` 组装统一响应
- 将 `pkg/errors.BizError` 映射为 HTTP 状态码

**禁止：**

- 直接操作数据库 / Redis
- 编写跨模块业务规则

### 2.3.2 Service 层（业务逻辑层）

**职责：**

- 业务用例编排与规则实现
- 调用 Repository 完成持久化
- 通过事件总线发布领域事件
- 事务边界控制

**禁止：**

- 直接写 SQL
- 绑定具体传输协议细节

### 2.3.3 Repository 层（数据访问层）

**职责：**

- 基于 GORM 实现数据的增删改查
- Redis、Lua 脚本等存储交互

**原则：**

- 只做数据存取，不包含业务规则
- 以接口形式向 Service 暴露，便于 mock 测试

### 2.3.4 Model 层（数据模型）

**职责：**

- 定义 GORM 持久化结构与表映射
- 提供向契约 DTO 转换的方法（如 `ToEvent()`），作为持久化模型与对外契约之间的防腐层

## 2.4 公共库与契约

### 2.4.1 pkg/errors — 统一错误体系

以错误码 + `BizError` 表达业务错误，`CodeToHTTPStatus` 负责错误码到 HTTP 状态码的映射。

### 2.4.2 pkg/response — 统一响应

统一响应结构含 `code`、`message`、`data`、`trace_id` 字段，全部服务一致使用。

### 2.4.3 pkg/eventbus — 事件总线

统一事件信封字段为 `event_id`、`event_type`、`timestamp`、`tenant_id`、`source`、`data`；主题命名为 `vocara.event.{type}`。提供 NATS、Redis、Dual（NATS 优先、Redis 降级）三种发布者。

### 2.4.4 pkg/middleware — 通用中间件

提供 TraceID、Recovery、CORS、RequestLogger、JWT、InternalAuth 等中间件。中间件链顺序为 TraceID → Recovery → CORS → RequestLogger → JWT。

### 2.4.5 pkg/license 与 pkg/version

- `pkg/license` 提供 License 验签、状态管理与到期 / 容量 / 模块开关拦截。
- `pkg/version` 暴露 `Version`、`BuildTime`、`GitCommit`，由构建期 `-ldflags "-X"` 注入。

### 2.4.6 contracts — 跨边界契约

`contracts`（module `vocara/contracts`）零第三方依赖，是双仓库共享、编译期稳定的接口面：

- `contracts/event`：`AllocatedCall`（queue.dequeue）、`CDRData`（cdr.created）。
- `contracts/call/v1`：callctrl 的 inbound 回调请求体，按 `domain/version` 组织版本。

业务侧依据契约开发，编译期不依赖核心区源码。自研 ESL 位于核心仓库 `esl`，全系统仅被 callctrl 引用。

## 2.5 模块间依赖关系

```
                 事件（queue.dequeue）
   ┌────────┐ ───────────────────────►  ┌──────────┐
   │  acd   │                           │ callctrl │
   └────────┘ ◄───────────────────────  └──────────┘
                  HTTP（内部令牌）            │
   ┌──────────────┐  HTTP（内部令牌） ◄──────┤
   │ agentcenter  │                         │
   └──────────────┘                  HTTP（内部令牌）
   ┌──────────────┐  ◄──────────────────────┘
   │    admin     │
   └──────────────┘
        事件总线 cdr.created / agent.status_change …
   ┌────────┐  NATS + Redis 事件   ┌──────┐
   │ 业务服务 │ ──────────────────► │ push │ ── WebSocket
   └────────┘                      └──────┘
```

**依赖原则：**

1. **事件解耦**：acd 与 callctrl 之间以 `queue.dequeue` 事件协作分配通话，不做 Go 侧同步调用。
2. **反向 HTTP 受控**：callctrl 作为客户端，以内部令牌（X-Internal-Token）调用 acd / agentcenter / admin。
3. **统一话单口径**：话单经事件总线以统一信封发布 `cdr.created`（主题 `vocara.event.cdr.created`），由 push 路由到 WebSocket。
4. **跨服务不直连存储**：服务间只通过 HTTP 或事件交互，不访问对方数据库。

## 2.6 工作区与构建

仓库根不是 Go 模块，禁止在根目录执行 `go build ./...`。两个仓库各持有一套工作区：

| 工作区 | use 范围 | 用途 |
|---|---|---|
| vocara 根 `go.work` | pkg、contracts、业务四服务 | 业务侧构建与联调，不含核心 |
| 核心仓库 `core/go.work` | ../vocara/pkg、../vocara/contracts、esl、callctrl、license-cli | 核心侧独立构建 |

独立构建：

```bash
# vocara 侧（本仓库根目录）
go build ./pkg/... ./contracts/... ./business/services/admin/... \
  ./business/services/agentcenter/... ./business/services/acd/... ./business/services/push/...

# 核心侧（在核心仓库 core/ 内执行）
go build ./callctrl/... ./esl/... ./tools/license-cli/...
```

vocara 顶层 Makefile 提供业务交付流水线，核心仓库 Makefile 提供核心构建与产物发布：

- `build-business`：业务四服务编译至 `dist/business`。
- `build-release`：归集核心预编译二进制 `bin/vocara-callctrl(.exe)` 至 `dist/business`。
- `package`：打业务 tar.gz（四个业务二进制 + callctrl 二进制 + 各服务 config）。
- 核心侧 `build` / `build-callctrl`：callctrl（静态编入 ESL）编译（linux + windows），统一 `-trimpath -ldflags "-s -w"` 并注入版本信息。
- 核心侧 `build-phonebar`：电话条混淆构建，产物与客户无关。
- 核心侧 `sync`：把 callctrl 二进制、混淆电话条、callctrl 配置模板发布到 vocara；FreeSWITCH 配置（fs-sbc / fs-agent conf）由运维从核心仓库 `freeswitch/` 目录直接部署。
